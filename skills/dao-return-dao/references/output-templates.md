# dao-return-dao 输出模板

这份文档提供 `dao-return-dao` 的可复用回答模板。

它不是新的规则，只是把 `SKILL.md` 里已经确定的结构，整理成更容易直接套用的说法。

## 使用提醒

套模板之前，先确认三件事：

- 现在真的是在问“要不要回母体”
- 当前对象已经被说清，不是整个项目一锅端
- 你不会一上来就跳去回答“放哪一层”

如果这三件事还没成立，先回到 `SKILL.md`，不要直接套模板。

## 模板 B：结论为“留在分支”时

```md
### 当前总判断
这东西现在先不要急着回主仓，它更像还长在 `[当前项目/分支]` 里的局部经验。

### 当前对象说明
当前要判断的是：`[对象]`
它目前主要来自：`[项目 / 分支 / 实践场景]`

### 归母判断标准
我还是按三条看：能否跨项目成立、是否真实验证、回去后是否让母体更清楚。

### 判断结果
我的结论是：`留在分支`
因为它现在还明显依赖 `[当前上下文]`，还没有足够证据证明它离开这个场景也能稳定成立。

### 归母落点建议
这一步先不谈回哪一层。
更合适的做法是把它留在当前分支里继续长，等第二个场景再看。

### 风险提醒
最容易出现的偏差，是因为它“现在很有用”，就误以为它“已经适合归母”。

### 下一步建议
1. 先在当前分支保留这条经验
2. 记录它依赖了哪些特殊上下文
3. 等第二个真实场景再重新判断
```

## 模板 C：结论为“候选观察”时

```md
### 当前总判断
这东西已经开始露出归母信号了，但我不建议现在就直接回主仓。
更合适的状态，是先把它放进“候选观察”。

### 当前对象说明
当前要判断的是：`[对象]`
它已经在 `[场景 A]` 里跑出来，并且在 `[场景 B / 第二次实践]` 里也出现了相似迹象。

### 归母判断标准
我还是按三条看：能否跨项目成立、是否真实验证、回去后是否让母体更清楚。

### 判断结果
我的结论是：`候选观察`
因为它已经不完全是单点偶然，但验证还不够稳，或者它回母体之后的表述还不够清楚。

### 归母落点建议
这一步先不正式归母。
可以先记成一条候选项，重点观察它在下一个场景里是否还能稳定成立。

### 风险提醒
最容易出现的偏差，是把“已经有通用感”误当成“已经成熟”。

### 下一步建议
1. 先记录它目前已经成立的部分
2. 补一个新的实践场景验证它
3. 等它的表达和边界更清楚后，再判断是否归母
```

## 模板 D：结论为“可以归母”时

```md
### 当前总判断
这东西现在已经不只是某条分支里的局部经验了，我认为它已经长到可以回母体。

### 当前对象说明
当前要判断的是：`[对象]`
它已经在 `[场景 A]`、`[场景 B]` 中被验证，并且正在对 `[某条旧定义 / 某层结构]` 形成稳定支撑或修订依据。

### 归母判断标准
我还是按三条看：能否跨项目成立、是否真实验证、回去后是否让母体更清楚。

### 判断结果
我的结论是：`可以归母`
因为它已经跨出单项目上下文，也经过了真实场景验证，回到母体后能够带来结构上的清晰，而不是内容堆积。

### 归母落点建议
接下来可以开始谈落点：
- 建议回到：`[L1 / L2 / L3 / L5 ...]`
- 建议动作：`[更新旧文档 / 新建新文档 / 作为修订依据并入旧定义]`

### 风险提醒
这一步最容易忽略的，不是“能不能回”，而是“回去之后怎么写才不把母体写糊”。

### 下一步建议
1. 先把它整理成一条最小可归母表述
2. 明确它对应的是新增，还是修订旧定义
3. 再进入具体文档落位
```

## 模板 E：日常对话轻量版

适合对方只是临时问一句，你不想一下子展开成完整长文时使用。

```md
这次我先不急着回答它该放进哪一层，先只判断一件事：`[对象]` 现在有没有成熟到可以归母。

我当前倾向：`[留在分支 / 候选观察 / 可以归母]`

原因很简单，主要看三条：
1. 它有没有跨出单项目上下文
2. 它有没有被真实场景验证
3. 它回去之后会不会让 Dao 更清楚

按现在的信息看，`[一句话说明结论]`

所以我建议下一步先：`[一句话建议]`
```

## 一句话原则

模板只是帮归枢把话说稳，不能替代判断本身。

真正要守住的只有三件事：

- 先判断成熟度
- 再谈回哪一层
- 不为了补主仓内容而误归母
