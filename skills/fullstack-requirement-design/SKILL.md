# 全栈需求分析与技术设计

让产品、设计、前端、后端、测试和运维从同一组业务场景出发，再分别看到自己要决定、实现和验证的部分。用户可以是一人全栈，也可以是多人团队；角色视角始终分开，信息源始终相同。

## 独立使用与项目适配

本 skill 自带需求梳理、设计、开发切片和验证交付方法，不依赖特定流程框架、其他 skill、任务卡系统或外部平台。仅有需求描述也可开始；缺少代码或历史记录时，将现状标为未知，先形成候选方案和待确认项。

项目已有工作流时，将本 skill 的交付物映射到其文档、状态和检查点；没有时直接使用下述工作顺序及迭代参考的最小闭环。不为使用本 skill 要求安装其他流程、创建专用目录、采用固定分支模型或先配置 Issue 平台。

## 适用方式

- **需求分析**：需求尚有空缺时，先还原现状、业务目标、场景和待决问题；不把建议写成已确认决定。
- **技术设计**：业务语义已足够明确时，形成跨端方案、依赖顺序和可验收切片。Nuxt/Next.js + NestJS 是默认参考栈，不强加给其他项目。
- **开发协作**：用户要求推进实现时，围绕已明确的场景和契约逐片实现、联调、测试与交接；发现需求或契约变化时回到对应设计，不自行扩展范围。只要求分析或设计时，交付到该边界。
- **变更评审**：对照已确认的场景和当前实现，说明修改了什么、哪些角色需行动或知会、哪些验收要重跑。
- **源码复盘**：沿场景追踪设计、契约、后端、前端、测试和运行证据；先让学习者预测，再对照实际代码校准。
- **已有项目文档重建**：从可用的代码、文档、版本历史和工作记录整理需求与分角色设计，明确哪些是历史决定、哪些是从实现反推的草案。需要教学知识库或接口补档时，按需读 [文档重建与交付视图](references/document-reconstruction.md)。

## 工作顺序

1. **核对现场**：读取用户提供的需求、设计及可用代码；按实际情况查项目约定、工作记录、版本状态及相关测试。标明来源与时间。缺少某种载体不阻止分析，旧文档和旧方案不能自动覆盖较新的决定或实现。
2. **建立共享语义层**：为每个可独立验收的场景编号，写清参与者、触发条件、前置状态、用户可见结果、业务状态变化、不变式、失败出口与验收例子。使用产品语言；此层不以页面、接口、表或字段命名代替业务含义。补一份消除歧义的术语表。
3. **投影角色视图**：每个角色都引用相同的场景编号和术语，只展开自身的决定与交付。产品看范围和规则；UI 看页面、状态、文案、可访问性；前端看交互状态、路由/SSR、请求与缓存；后端看权限、契约、持久化、事务与并发；测试看正反例和回归；运维看迁移、配置、发布、观测、数据保留与回退。没有影响时写明原因，不生成空洞设计。
4. **形成技术方案**：先定跨端契约和状态转换，再决定哪些变化落在各应用、共享包与数据库。数据结构变化不必然意味着建表或改表；逐层核对真实影响。保留有取舍的方案、采用理由、兼容性和未决项。
5. **按影响切片和验收**：把需求拆成能独立验证的纵向用例，为每片连接场景、角色交付、测试证据与回退办法。顺序由依赖决定，可以并行做已稳定契约下的前后端工作；不机械规定后端全部完成后前端才能开始。

使用 [输出形状与变更判据](references/design-package.md) 组织结果。按任务规模裁剪，不要求固定文档数量；已有 PRD、Issue、设计文档或任务卡时，优先在其职责内更新，避免维护平行事实源。

## 交付选择与迭代衔接

- 开始时说明采用哪种方式、本轮交付物和验证边界。既有项目可以同时有复盘与新设计，但要分清哪些是实现事实、哪些是建议；资料不足时先交缺口和可继续部分。
- 产品规则只在共享场景定义一次；前端设计说明交互如何兑现它，后端设计说明服务如何保证它，API 固定双方的输入输出与错误语义。具体提纲见设计参考，不以文件清单代替技术交接。
- 把场景、决定、契约、实现和验收证据串成可追踪关系；计划中的测试与实际运行结果分别记录。实现或环境变化时更新受影响的关系，不复制一整套任务状态。
- 需要推进开发、安排迭代、判断开工/完成或验证本 skill 时，按需读 [迭代交接与试用验证](references/iteration-validation.md)。设计可交接、实现通过测试、人工验收和生产上线分别判断；已有流程只作为可选适配。

## 变更传播

对每次需求变化先回答：改变的是**呈现**、**本地交互**、**跨端契约**、**持久化数据**、**业务规则/权限**，还是**运行与发布**？一项变化可同时属于多类。

- 仅视觉呈现：UI、前端与测试核对；产品是否需确认取决于它是否改变已定体验。
- 仅客户端交互：UI、前端与测试核对；若改变请求时机、错误语义或可访问数据，继续检查后端和契约。
- 契约、持久化结构、业务规则或权限变化：向所有角色同步共享场景的变化；各角色再确认自身是否需要修改、复测或仅知会。尤其检查旧数据、旧客户端、迁移及回滚。
- 运行、隐私或发布变化：把运维与安全/合规相关决策纳入受影响视图；不要把“写在设计中”当作“已部署并验证”。

影响结论用“需修改 / 需知会 / 无影响（附依据）”表达，不以“前端需求”“后端需求”给整项需求单一定性。变更后更新共享场景与受影响的角色视图，并标明替代了哪一条旧决定。

## 过门与证据

- 始终区分**候选、已确认、已实现、已验证**。源码存在不代表交互被验收；设计记录也不代表功能已实现。
- 业务目标、范围、关键状态或验收含义不明确时，先给当前理解与少量会改变设计的关键问题；独立部分继续分析，依赖该决定的实现暂不推进。
- 涉及数据库、环境变量、CI/CD、发布或外部写入时，遵守当前项目的授权与回滚约定；本 skill 本身不授予执行权限。
- 交付前检查每个关键场景能否追到设计决定、代码位置、测试或人工验收、运行风险。发现断链时说明缺口，不伪造通过记录。
- 指导学习时每轮只走一个场景或一段链路：先问学习者“下一层应该保证什么”，再读源码，最后用失败例子检验理解。
