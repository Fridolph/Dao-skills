# 已有项目的文档重建与交付视图

用于“给已实现项目补需求、前端设计、后端设计、API、教学资料”或“整理到知识库”的任务。新需求仍按 SKILL.md 的共享场景与角色视图处理。

## 证据先于完成度

记录可获得的基线版本、采集日期与来源。版本历史表明提交了什么，Issue 等工作记录表明协作状态及承诺，源码表明当前行为，环境验证表明在哪里实际成立。它们不能互相替代；未使用某种工具时直接采用已有材料，无需补建该工具才能重建文档。

旧文档与新实现不一致时，核对同一任务的后续记录；区分原始设计、最终决定、当前实现、验证记录、未决问题。关闭 Issue、任务卡 done、测试文件存在、构建成功均不能独立证明生产已可用。后续记录补齐环境问题后，也不能继续引用更早的暂停结论。

从实现反推的需求/设计标明“文档重建，待产品复核”，不编造过去举行过评审、执行过 Sprint 或完成过上线。无法读取远端时说明查询边界，不把本地 tracking ref 称为实时 GitHub 状态。

注释、方法名和任务描述是意图线索，需与运行时 schema、执行分支及测试断言对照。出现冲突时分别记录“期望保证”和“当前行为”，不要在补文档时把差异悄悄修饰成一致。沿跨请求链路核对具体值能否被下一步消费，以及中途失败前是否已有写入；单个方法看似正确不能证明整体业务成立。

## 文档承载分开，语义保持同一份

沿用已有文档位置，按规模选择合并章节或拆页；跨文档使用稳定场景编号。不要另造一套状态台账。

| 文档视图 | 必须澄清的责任 |
| --- | --- |
| 共享需求 | 谁在什么状态触发什么、得到什么、规则/非目标、失败出口、验收样本 |
| UI 与前端设计 | 用户可见状态、路由/SSR、组件/工作副本/缓存、请求时机、失败恢复、可访问性、桌面/移动验收 |
| 后端设计 | 身份/权限/所有权、输入输出、状态变化、持久化、事务/并发、兼容/迁移与回退 |
| API | 方法/实际路径、schema 来源、必填/缺省/nullable、响应包装、错误、鉴权、幂等/重试、二进制/上传、示例与覆盖缺口 |
| 实现与源码导读 | 真实文件职责、契约与调用链、关键决定的落点、提交与设计偏差；不大段复制源码 |
| 测试与交付 | 用例计划与执行证据分开；环境/版本/时间/结果/缺口，部署依赖、观测与回退、验收责任 |

前端需求描述用户行为与反馈，后端需求描述服务保证，双方引用共享业务规则。不能把前端设计缩成字段表，也不能在前后端两页各自定义业务状态。输入字段变化应逐层核对是否真的需要迁移。

API 目录与完整机器契约是不同交付物。对照 Controller、运行时 schema、实际返回与全局包装；从生成脚本名或旧 OpenAPI 文件存在不能推断全量覆盖。只登记错误码、限流、权限、默认值等已核对事实；未验证的示例明确为合成样例。

## 从文档进入真实学习与迭代

先交功能地图及少量可审阅切片，按用户期望范围逐模块补齐，不用模板数量代替设计。每轮教学只走一条场景：先让学习者预测，再对照源码，用失败例检验；教材存在不等于学习者完成验收。

对真实增量需求，连接需求评审、验收用例、分角色技术评审、实现、联调、测试、交付与复盘；按需使用 [独立运行的最小闭环](iteration-validation.md)，或适配项目已有工作流。自动化验证和业务/交互验收分别记录，不额外强制任务状态或固定审批。

发布/知识库页面写入、Issue 变更、部署或数据库操作各自遵守项目授权。若只请求拟文档，先提供可阅读草案；已有明确执行授权则继续完成，不重复请求许可。知识库与仓库两处维护时明确编辑源、同步责任和源码 permalink，避免双份规则漂移。

skill 改进以本次真实失误或观察为依据，项目细节留项目；一次文档试用只能证明这次产物可审阅，不能宣称已通过独立行为评测或正式成为跨项目规范。
