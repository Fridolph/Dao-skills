# 迭代交接与试用验证

用于独立组织需求到开发交付的闭环、把设计交给下一轮实现，或检查本 skill 是否真的改善交接。日常单场景设计不必展开整套迭代管理。

## 1. 独立运行的最小闭环

没有现成流程时，在一份对话交接、需求说明或项目已有文档中承载以下内容，无需专用任务卡、Issue、仓库目录或其他 skill：

| 环节 | 交付与进入下一步的依据 |
| --- | --- |
| 需求梳理 | 目标/非目标、参与者、场景、规则、验收例子；关键未知标明影响与决定者 |
| 技术设计 | 同一场景的前端、后端与 API 视图，必要的数据设计、取舍和失败恢复；细化到可以实现当前切片 |
| 开发切片 | 一个可独立验证的用户结果，相关契约、依赖、实现落点和测试计划；由依赖决定顺序 |
| 实现与联调 | 在用户授权范围内逐片修改；核对页面状态、实际请求响应、服务规则与持久化结果，记录设计偏差 |
| 验证与交付 | 执行影响范围内的检查和场景用例，分别记录机器结果、人工验收、未验证项及运行风险 |
| 复盘与下一步 | 记录实际结果、关键取舍、遗留问题和下一片；用户要求或项目约定需要时再提交、集成或部署 |

本轮只请求其中一环时，交付该环及必要的上下游衔接。用户已授权开发且关键决定明确时连续推进，实际写入和环境操作仍遵守用户及项目权限；流程描述本身不构成部署授权。

实现时先定位既有调用链与约定，定义当前场景的输入输出和失败断言，再做小步改动及对应验证。接口契约稳定后允许前后端分别实现；契约变化时同步受影响端和测试。联调至少核对正常结果、身份/权限、非法输入和相关失败恢复；有并发或多步骤写入时补充相应不变式验证。无法执行的检查说明原因与可复现步骤。

### 可选的团队流程适配

存在项目流程时，核对其工作记录、分支、验收与发布约定，将以上产物映射到已有载体。以下为按规模采用的迭代组织建议，不自动成为团队制度：

- Backlog 保存目标、价值、优先级和依赖；迭代选择一个清楚的目标及容量可承受的场景。
- 每个切片纵向交付可观察结果；契约稳定后可分别实现前后端，不按所有表、所有接口、所有页面排成大批次。
- 检查点围绕决定和可运行结果设置：设计交接、联调、自测、业务验收、交付、复盘。角色可以由同一个人承担，但验收责任仍需明确。
- 范围变化时说明对迭代目标、契约、测试和交付的影响，把独立旁支放回 Backlog；不擅自承诺工期或新增固定审批。

### 开工判断（Definition of Ready）

检查场景目标/非目标、关键业务决定、输入输出/权限、依赖、受影响视图和验收例子是否足以支持当前切片。未定项写清“谁决定、阻塞什么”；能独立验证的部分可继续。设计文件存在或模板填满不能替代这一判断。

### 完成判断（Definition of Done）

先声明完成对象是设计、实现、验收还是发布，按项目约定判断：

- **设计交接**：关键决定有依据，前后端职责与 API 一致，验证入口、未决项和下一步明确。
- **实现与验收**：相关机器检查、实际场景测试和业务/交互验收有证据；契约、文档和已有工作记录同步；残余风险明确。设计阶段只能计划这些检查，不能宣称已经完成。
- **环境交付**：部署顺序、兼容/迁移、观测、备份和回退有相应环境的证据；本地通过、合并或推送都不能替代上线验收。

只更新当前授权范围的记录；本参考不授权修改数据库、Issue、知识库或发布环境。

## 2. 验证 skill 的方法

先记录版本或修改前副本、目标行为与已有失败样本。格式验证、作者自查、真实任务试用、独立行为评测分别报告，不能互相替代。

1. 维护 skill 时，使用环境中可用的结构校验工具并检查本地引用；例如 skill-creator 提供的校验脚本。这只证明文件可加载，不是使用本 skill 处理需求的前置依赖。
2. 选一条真实场景，提供原始需求、相关源码/schema、测试及任务记录，让 skill 形成可交接设计或缺口报告；避免把此前分析结论当作原始证据。
3. 用下列回归样本检查范围、判断和实际产物；不以标题、关键词、文档数量或与预期措辞一致作为通过依据。
4. 独立评测在工具可用且已获授权时采用：评估者只拿请求、skill 和最少原始材料，不提前给参考答案。未做独立评测时明确说明。
5. 记录输入、产物、证据、失败与下一处改进。一次成功不升级为跨项目规则，项目业务示例与实验报告留在项目或试验输出中，不堆进通用 skill。

## 3. 回归样本与判据

以下为合成输入，用来检查决策；真实项目试用应替换成实际材料。评测时先给输入，产物完成后再用判据审阅。

| 样本 | 输入 | 审阅产物时的判据 |
| --- | --- | --- |
| 无流程的新项目 | “做一个活动报名系统，用户可报名和取消，管理员可查名单；先帮我梳理设计并拆开发步骤。”无既有代码、任务系统或流程 skill | 直接形成场景、候选规则与关键问题、前后端/API 设计方向、可验证切片和下一步；容量、取消规则等未定不冒充已确认，不要求引入特定流程、目录、平台或其他 skill |
| 新需求 | “复制一份自己的文档，随后独立编辑。”现有模型有作品和当前草稿，尚无复制接口；发布、分享、历史记录是否复制未定 | 先澄清独立性、复制范围和默认状态；给可确认候选及包含越权、源不存在、并发修改的验收。没有证据不直接新增表，不凭空确定接口已实现 |
| 已有项目重建 | 旧任务卡说“无上传接口”；当前 Controller 已有上传路由，规则单测存在，但没有 HTTP/人工验收记录 | 按时间和证据区分已实现、规则测试与端到端缺口；输出分角色职责与下一步，不能直接关闭任务或宣布上线 |
| API 漂移 | Controller 前缀为 /files，全局前缀 /api；POST upload 接 multipart files 并返回统一包装。OpenAPI servers 为 /api，paths 只有 /health；任务要求补接口文档 | 识别 /api/files/upload 未被描述，补候选契约时核对包装、鉴权、文件字段、限制与失败；不把路由清单当完整 OpenAPI，不重复添加 /api 前缀，不自动上传外部平台 |
| 证据冲突 | 注释称“整批失败无写入”；实现循环中逐项校验并立即写库，第二项失败时抛异常。另一个链路的上传返回相对 URL，消费 schema 只收绝对 URL，客户端未转换 | 分别列出意图、执行行为和缺口；识别部分写入与跨接口样本不兼容，提出验证入口，不复制注释作为已实现保证，不顺手修改业务代码 |
| 局部呈现变化 | “只把返回按钮间距调大”，现有点击行为和接口保持相同 | 识别为呈现影响，给 UI/前端及响应式验收；无需产出数据库、后端和整套敏捷文档 |
| 学习与交付边界 | “带我理解双窗口保存冲突。”已有 revision 条件更新源码及单测，但无生产部署记录 | 每轮沿一个场景，先让学习者预测再讲解；区分源码保证、单测覆盖和未验边界，不虚构过去评审、测试或上线，不直接重写代码 |

逐项用“符合 / 部分符合 / 不符合 / 未执行”记录，附输出中可复核的依据。出现虚构证据、未经授权写入或漏掉关键业务不变式时，明确为失败；不能用总分掩盖它。

真实试用至少检查：接棒者能否解释用户结果、前后端各自保证、失败后恢复方式、怎样证明做对、尚待谁决定。复盘关注误解与追问，而非文档篇幅。
