# 输出形状与变更判据

这是一份可裁剪的工作底稿，不是必须逐栏填满的表单。把团队已有文档作为载体；本参考只规定各角色如何保持同一语义。

## 1. 共享场景

先记录来源、日期、当前事实、确认者，以及每条结论的状态（候选 / 已确认 / 已实现 / 已验证）。给每个场景一个稳定编号，例如 `S1`。

| 场景 | 参与者与触发 | 前置条件 | 可观察结果 | 业务状态变化与不变式 | 失败出口 | 验收例子 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | 谁在什么情况下做什么 | 什么条件必须先成立 | 用户/其他系统看到什么 | 什么能变、什么绝不能变 | 拒绝、失败、冲突后怎样保持或恢复 | Given / When / Then，含反例 |

先使用业务词。另列术语表，区分容易混淆的概念，例如“公开简历”和“受控分享链接”。当需要多个页面或接口时，它们可以服务同一个场景；不要按文件数拆场景。

## 2. 角色视图

每个视图引用 `S1` 等场景编号，不重新改写业务定义。按实际影响填写：

| 角色 | 要回答的问题 | 常见交付 |
| --- | --- | --- |
| 产品 | 为谁解决什么问题；范围、规则、边界和优先级是什么 | 业务决定、验收口径、非目标 |
| UI/交互 | 用户在哪些状态看到什么、能做什么；桌面和移动端如何表达 | 状态图、页面/组件行为、文案、可访问性 |
| 前端 | 用户动作怎样变成状态和请求；失败、并发、缓存、SSR 怎么处理 | 路由/组件职责、状态机、请求映射、错误反馈 |
| 后端 | 谁可执行；输入输出和错误是什么；持久化、事务、并发由谁保证 | API 契约、服务规则、数据模型、迁移判断 |
| 测试 | 哪些正例、反例、权限、边界与回归能证明场景成立 | 用例矩阵、自动/人工验收、证据入口 |
| 运维 | 变更如何进环境、观察、回退；数据如何保留和清理 | 迁移与发布步骤、配置/监控/告警、回退及保留计划 |

角色是一种审阅视角，不要求团队真的有六个人。一个人负责多角色时，仍分别检查其问题。

## 3. 技术设计与决定

先画一次场景的数据流和状态转换，再写必要的实现落点。对 TypeScript monorepo，至少核对：

- `apps/web` / `apps/admin` 的用户入口、可见状态与身份；Nuxt/Next.js 的 SSR、路由和缓存边界；
- 共享契约落在何处，前后端对输入、输出、错误码、可空/缺省值如何达成一致；
- NestJS 的 Controller、Service 与授权条件；是否需要 Prisma schema、migration、事务或并发控制；
- 自动测试、桌面/移动端人工验收和异常路径；
- 部署顺序、旧数据/旧客户端兼容、观测、隐私保留与回退。

只展开被当前场景触及的项。决定记录可用下表：

| 场景 | 待决问题与方案 | 采用结论及理由 | 受影响角色 | 兼容/迁移/回退 | 状态与依据 |
| --- | --- | --- | --- | --- | --- |
| S1 | 真正有取舍的选项 | 选择及代价 | 谁要行动或知会 | 有则写，无则说明 | 谁在何时确认；代码/测试证据 |

### 前端技术交接

逐场景回答以下问题，可合并进现有设计页：

- **入口与职责**：谁访问哪个路由，页面、业务组件、共享组件及 composable 各负责什么；说明 SSR/客户端执行边界。
- **状态与动作**：加载、空态、只读、编辑、提交中、成功、失败和冲突分别看到什么、能做什么。标明服务端数据、编辑工作副本与本地临时状态的归属。
- **请求与恢复**：动作对应哪个接口，校验何时发生，重复点击、乱序响应、自动保存、取消/离页和失败重试怎样处理；只展开当前场景实际涉及的情况。
- **缓存与反馈**：查询 key 的业务维度、成功后刷新谁、鉴权失效如何恢复；字段错误、全局错误与 traceId 如何呈现，避免重复提示。
- **验收**：桌面/移动、键盘操作和关联异常路径；引用共享验收规则，不在此重新定义业务含义。

### 后端技术交接

- **信任边界**：调用者身份从哪里恢复，角色权限与资源所有权分别在哪里判断；不把前端禁用按钮作为服务端授权。
- **用例流程**：用程序化伪代码表达输入 → 认证/授权 → 校验 → 条件分支 → 读写 → 返回/失败出口；注明事务边界、并发条件、幂等或重复请求策略。
- **数据与约束**：已有模型能否承载；字段、关系、索引、唯一约束与 JSON 文档各保证什么。只有确需改变持久化结构时才设计迁移，注明旧数据兼容与回退限制。
- **模块与契约**：Controller/Service/持久化职责和跨模块依赖；输入 schema、输出投影、敏感字段过滤与错误映射的来源。
- **验收与运行**：正反例、跨用户访问、并发及必要的数据库/HTTP 验证；相关日志、外部副作用与清理责任。

### API 交接

每个受影响操作至少澄清：

| 部分 | 内容 |
| --- | --- |
| 身份与地址 | 场景编号、方法、实际 URL（含全局前缀/版本）、认证、授权与所有权规则 |
| 输入 | headers/path/query/body、编码方式，类型/约束、必填/缺省/可空；省略、null、空字符串语义有别时逐项说明 |
| 输出 | HTTP 状态、统一响应包装、字段 schema；文件下载的 Content-Type/文件名及上传 multipart 字段另列 |
| 失败 | HTTP 状态与业务错误码、触发条件、客户端可采取的动作；只登记已确认或已核对的规则 |
| 副作用 | 写入范围、并发/幂等、重试条件、兼容影响；限流等机制只在有依据时列明 |
| 例子与来源 | 正常与关键失败示例、schema/类型定义、机器文档位置；区分合成示例与脱敏实测样本 |

API 目录只是操作索引，不能替代完整契约。核对路径/方法覆盖后，还要核对字段、权限、包装与错误语义；OpenAPI 的 servers/base path 与 paths 合起来才是请求地址。共享 DTO/Zod、Controller 与机器文档有差异时列明缺口，不选一个文件便宣称其余自动同步。

多个操作串联时，用一个具体样本追踪上一步输出、客户端转换与下一步输入校验；尤其核对 URL、ID、单位、枚举和可空值。区分“请求整体报错”与“没有产生任何副作用”，不要仅凭异常出口或注释推断事务原子性。

## 4. 变更影响表

以**上一次已确认的场景与契约**为比较基线。先说明差异，再填角色影响；不要凭文件名推断影响。

| 变化及场景 | 产品 | UI | 前端 | 后端 | 测试 | 运维 | 需要更新的契约/证据 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 只改按钮间距或颜色 | 按体验决策知会或确认 | 修改 | 修改 | 无影响：无请求/规则变化 | 视觉与响应式复测 | 无影响 | UI 规范与截图 |
| 客户端局部展开方式调整 | 按体验决策知会或确认 | 修改 | 修改 | 无影响：请求及数据不变 | 交互/键盘/移动端复测 | 无影响 | 交互状态与用例 |
| 改为保存新字段或新结构 | 确认语义 | 核对呈现和编辑 | 修改读取/写入 | 核对契约、校验、持久化；按需迁移 | 正反例、旧数据和跨端回归 | 核对迁移/兼容/回退；按需行动 | 共享场景、API、类型、数据模型、验收 |

每格用“需修改 / 需知会 / 无影响（依据）”。示例不是自动分类规则：若颜色承载业务状态，产品与测试也需重新确认；若交互改变请求顺序，后端也需审查。

## 5. 切片与交接

每个切片至少回答：交付哪条场景、依赖什么决定或契约、各端交付什么、用什么证据验收、失败如何回退。只有相关角色参与详细实现，但所有角色能从场景编号与变更表理解整体变化。

源码复盘时沿一条场景走：`需求原句 → 共享场景 → 设计决定 → 契约 → 后端状态变化 → 前端可见行为 → 测试 → 运行证据`。每一步都问“上一层的承诺由谁保证”；发现文档、代码、测试不一致时，标明时间和证据，先核实当前事实。

可在现有任务卡或设计页维护以下追踪关系；填已有锚点，不要求另建台账。一个场景可对应多个接口和用例：

| 场景/验收例子 | 决策与状态 | 契约锚点 | 前后端实现锚点 | 验证计划 | 执行证据与缺口 |
| --- | --- | --- | --- | --- | --- |
| S1 / A1 | 谁确认、当前结论 | API、schema 或类型 | 当前文件/提交；尚未实现则明确 | 用例、环境和验收责任 | 版本、环境、时间、结果；未执行明确标注 |

设计阶段允许实现和证据为空，但要给出验证入口；复盘阶段不能将空白补成虚构的历史。任务整体测试通过不等于每条场景已覆盖，引用测试时说明它实际断言了什么。
