# 锚点回看设计（设计候选）

> **状态：候选，未验证。** 本文件是 dao-commit 从"提交锚点"延伸到"回看与觉知"的设计基线，用于后续工具设计的共同参照。
> 它**不是运行时指令**：起锚规则仍以 `SKILL.md`、`core-protocol.md` 与 `references/64卦选择检查.md` 为准。
> 本文件不改变任何起锚判断，也不参与定锚。

## 0. 这份文档要解决什么

`dao-commit` 已经能给人提供一层"当时处境"的语义锚点。但锚点写完之后，它只是躺在 git 历史里。

这份设计要回答的是：**锚点积累起来之后，怎样回看才有意义、又不至于变成新的负担。**

它要同时守住三条底线：

1. **不骗人**：不能把数据 bug 读成"我的判断在进化"。
2. **不夺权**：统计只能呈现，不能给出选卦结论。
3. **不添负担**：它是为省事而来，若为维护工具而维护工具，就不值得做。

## 1. 先定性：它相对 git log 多出什么

报告的价值不在图形，而在**多出来的维度**。若只做到 git log 的重新排版，就不必做。

| | `git log` 能给 | 锚点额外给 |
| --- | --- | --- |
| 记录对象 | 文件怎么变的 | **系统处在什么局面** |
| 时间单位 | 每次提交 | 集成锚点（净变化） |
| 可回答的问题 | 谁、何时、改了哪些文件 | **这一轮把什么往哪推了一步** |
| 是否含判断 | 否 | **是**（选卦或处境描述就是一次判断） |

一句话：**`git log` 是活动史，锚点是处境史。**

### 1.1 "能否随时重新锚点"——一半可以，一半绝对不可以

这是设计上最关键的一次分界。既然 git log 是全的，直觉上似乎可以随时用同样的记录重新起锚。答案是：

- **事实可以完全重算。** hash、日期、diffstat、原始 subject 都是 git 派生物，任何时候重跑都一样。
- **判断不可重算。** 当时的处境判断是**当时的产物**，它取决于当时对系统的理解，也取决于**当时所依据的卦库版本**。

后者有活例：`trigrams.json` 在 v5.1.0 曾把 64 卦中 56 条的上下卦值整体填反，v5.2.0 才修正。如果今天用修正后的卦库去重读当时写的 `[☰☲][大有]`，会得出"当时判断错了"的结论——但当时依据的卦库本身就是错的。**这个结论在当时并不存在。**

所以：**可重算的归事实层，不可重算的必须冻结。**

## 2. 三层时间模型

这是整个设计的地基，做错了后面全废。

| 层 | 内容 | 可变性 | 来源 |
| --- | --- | --- | --- |
| **① 事实层** | commit hash、日期、diffstat、原始 subject、scope、type | **可完全重算**，任何时刻重跑一致 | git 派生 |
| **② 当时层** | 锚点 header（上下卦符号 + 卦名）、当时依据的 `trigrams.json` 版本 | **冻结，不可改** | 已烧进 git 历史 |
| **③ 今天层** | 对那一笔的评级、注解、"后来是否应验" | **只追加，不覆盖** | 人事后填写 |

### 2.1 为什么 ② 层必须 pin 版本

每条锚点应记录 `trigramsVersion`。这样即使卦库后来修正，也仍能解释"当时为什么这么写"。

没有这一层，半年后系统会**用未来的卦库去解读过去的判断**，得出一个当时根本不存在的结论——这正是本仓已经踩过的那次坑。

### 2.2 ③ 层的额外价值

③ 层的注解带时间戳，所以**回看本身也能被回看**。三个月前写"这笔作渐卦，贴切"，今天可能不再同意。于是得到的不是"卦象序列"，而是**判断的演化史**——比序列高一个维度。

## 3. 完备性与纠偏：不改历史，只作声明

### 3.1 不可篡改从哪来

不需要另造机制。锚点是**事实 + 判断**的组合：

- 事实部分绑定在 commit hash 上；
- 判断部分写在 commit message 里，**改动它就会改变 hash**。

因此 `git log` 的 hash 链本身就是完备性证明。任何对历史的重写都会在 hash 上暴露。

### 3.2 历史改不了，冲突只能靠"声明"

已经写进历史的错误符号，**不能也不该改写**。解决办法是追加一份**纠偏记录**（append-only），声明而不修改：

```text
anchor <hash> | 当时写入 [☴☲][鼎] | 判定: 符号反置 | 应为 [☲☴] | 原因: 依据 v5.1.0 反置数据
```

### 3.3 三类必须分开（否则会自我欺骗）

这是最容易出错、也最危险的一处。同一份记录里，看起来相似的三件事性质完全不同：

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| **A. 本来就对** | 符号与卦名一致 | 无需纠偏，但要记入以证明"核对过" |
| **B. 数据 bug** | 依据的卦库当时是错的 | 纠偏声明，注明依据版本 |
| **C. 判断演化** | 同一个人在不同时期对同类处境给了不同判断 | **不是错误**，是 ③ 层素材 |
| **D. 重复记录** | 同一笔因 rebase / amend 留下多条 | 按事实层去重，不计入判断统计 |

**把 B 读成 C，就是最危险的一种自我欺骗**——会以为自己"认知在进化"，实则只是当时数据坏了。反过来，把 C 当 B 抹掉，就丢掉了真正有价值的判断演化。

### 3.4 实测：现有数据里哪几类真的存在

对一份真实的内容型项目做过核对，29 个锚点：

- **A 类 20 条**：符号与卦名一致。
- **B 类 9 条**：上下卦反置（例：`[☰☲][大有]` 应为 `[☲☰]`）。成因明确，属 v5.1.0 反置数据。
- **C 类 0 条**：**至今没有样本。**
- **D 类 3 组**：同一 subject 各出现两次。

这里要更正一个流传的判断：那 3 组重复锚点曾被读作"同一状态、两个不同的卦"，并被视为天然的"判断漂移对照实验"。**实测中它们的卦名完全相同**（离/离、谦/谦、贲/贲），是 rebase 残留，属 D 类，不是 C 类。

这件事本身就是设计依据：**如果不把四类分开，D 类会被误当成 C 类的证据，进而得出"判断会漂移"的假结论。**

## 4. 从"哪次最像"改为"当期纠偏"

### 4.1 被否掉的方向

"历史上哪一次处境最像现在"看起来很美，但有两个问题：

1. **主观处境没有天然的相似度度量。** 用什么算"像"？卦名？diffstat？变化类型？任何选择都是一种人为设定。
2. **它天然滑向推荐。** 一旦系统说"这次最像第 7 笔"，人就会倾向照抄第 7 笔的判断——**这等于把定锚权交给了统计**。

### 4.2 改用的方向：当期自检

不做历史相似度匹配，改为对**当前这一笔**给出两侧对照，让人自己看：

- **事实侧**：净行数、文件与目录分布、新增 / 修改比例、与近几笔的规模对比、时间间隔。
- **判断侧**：这次准备写的处境描述与卦名。

输出的是"两侧是否自洽"的提示，**不是结论，也不是候选卦**。它的目的是**帮人看清当前处境**，而不是告诉他该选什么。

用一句话概括：**不是"看相似"，而是"客观找回自我"。**

## 5. 认知偏差检测（双轴对照）

这是整套设计里最有价值的增量维度。

### 5.1 它要捕捉什么

人对自己工作的描述，与工作本身的客观形态，经常不一致。典型形态：

> 以为是在慢慢打基础、整理归位，事实上一次性加了几万行。

这不是撒谎，是**认知偏差**。系统识别出来，本身就是一种觉察觉知。

### 5.2 实测案例

同一批 29 个锚点中，按"主观语义偏收敛、客观规模巨大"筛出的样本：

| 处境（卦） | type | subject 的动词 | 净增行数 |
| --- | --- | --- | --- |
| 谦（谦虚收敛、低位承重） | `docs` | 归位…并补齐 | **19,830** |
| 丰（丰盛、收束） | `feat` | 收束…并贯通 | **28,496** |
| 大有（丰收、成果） | `docs` | 收口…精校 | **18,451** |
| 渐（渐进） | `docs` | 体例统一 | **7,708** |

`谦` 那一笔最典型：卦义是收敛克制，type 是 `docs`，动词是"归位/补齐"——**主观语义全在"整理"，客观却是近两万行净增**。这就不是打基础，而是大规模扩建。

### 5.3 怎么设计才不越界

做**双轴**，不做**评分**：

- **轴 A（主观）**：卦义的方向、subject 动词的轻重。
- **轴 B（客观）**：净行数、文件数、新增与修改的比例。

两轴**偏离度高 = 认知最模糊处**，值得回看。但**偏离本身不是错**，也不是要被打分的指标。系统只把它标出来，不给结论。

> 反例警戒：一旦做成"偏离度评分"，人就会为了让分变好看而调措辞——又回到机械映射的老路。

## 6. "64 格覆盖"要重新理解

### 6.1 被否掉的读法

把"点亮了多少卦"当作**覆盖率指标**是不合理的：

- 一个系统**不一定**需要占满 64 卦；
- 更根本的是，"有没有用过未济卦"与"系统是否处在未济的处境"是两件事——**可能从未写过未济，但系统本身就是一个未济的体现。**

用覆盖率取象，等于让人去凑格子。

### 6.2 改用的读法：语言分辨率自识

覆盖图只作**镜像**，不作指标：

- 它回答"我这套语言表达过哪些处境"，不回答"我表达得够不够全"。
- **空白不是缺口**，而是"尚未被这套语言捕捉的处境"——可能本来就不需要捕捉。
- **集中本身是信息**：实测 29 个锚点只用了 13 个卦，且高度集中于少数几个（大有 7、谦 4、鼎 3、贲 3）。这恰好说明那段时期的系统处境类型比较单一（内容扩建 + 体例收束），是**真实的处境描述**，不是"用偏了"。

## 7. 红线：不参与定锚，只参与回看

> **回看系统绝不参与定锚，只参与回看。**

具体做法：

- **不呈现**："你选得太集中了""建议换个卦""这个机会适合 X 卦"这类判断。
- **可以呈现**："你上次在类似处境选了什么、后来怎样了"。

理由：一旦统计开始给结论，**定锚权就从人转移到了统计**，机械映射换一个更隐蔽的形式回来了——而那正是之前几轮修复要革掉的东西。

这条线守住，它是镜子；守不住，它就是新的指挥棒。

## 8. 维护成本：留白即机制

### 8.1 三个敌人

| 敌人 | 表现 | 对策 |
| --- | --- | --- |
| 录入成本 | 每笔要填十个字段，没人会填 | **每笔只新增一个必填：一句话。**其余全自动 |
| 数据腐坏 | 卦库会变、口径会变，半年后自相矛盾 | ② 层 pin 版本 + ③ 层只追加 |
| 无人触发 | 手工跑的脚本活不过三周 | **留白本身作为待办机制** |

### 8.2 为什么留白是机制

不能靠自动起卦——**判断必须由人给出**。所以自动化只能填 ① 层，② 层与 ③ 层必须留空。

而留空正好形成驱动力：系统持续显示"29 个锚点里还有 N 个没有回看"，这张待办自然存在。**动力来自空缺，不来自完整。**

反过来说：**这个系统不该追求"完整"。** 它应该永远显示"还差多少没看"。

### 8.3 活性指标

> **回看覆盖率 = 被事后评过级的锚点数 / 总锚点数**

当前是 **0 / 29**。如果三个月后仍是 0，说明做了一个漂亮但没人用的东西；如果到了两位数，它才算活了。

真正的价值从来不在自动算出来的那部分，而在**人愿意往上填的那部分**。

## 9. 它最终要回答什么

综合以上，回看面要回答的不是"数据完不完美"，而是两件事：

1. **当前的问题在哪里**（自洽性、认知偏差、需要回看的锚点）。
2. **与未来的方向是否匹配**。

第 2 点需要补充一个接口：**系统无法自行知道"方向"是什么**，必须由项目侧声明（路线、愿景、阶段目标）。没有这个声明，"是否匹配"无从判断。这不是自动可得的数据，是需要人给的一个输入。

## 10. 屏幕收敛（设计输入，非最终形态）

| 屏 | 看什么 | 状态 |
| --- | --- | --- |
| ① 当期自检 | 当前集成单元的事实侧 ↔ 判断侧对照（纠偏） | 方向已确认，**做法已从"找最像"改为"当期自检"** |
| ② 轨迹与语言分辨率 | 处境序列、月度节奏、覆盖图（作镜像，非指标） | 方向已确认，**读法须按第 6 节修正** |
| ③ 审计 | 格式合规 / 符号纠偏 / 重复锚 / 主观↔客观偏离度 | 认可，偏离度为最优先增量 |
| ④ 回看 | 每笔的评级、注解、判断演化史 | 认可 |

## 11. 明确不做

- 不做历史相似度匹配，不做"建议卦象"。
- 不做覆盖率 / 偏离度 KPI 化。
- 不改写历史锚点（只追加纠偏声明）。
- 不自动起卦、不自动填写判断层。
- 不为展示效果增加字段或图形。

## 12. 与 dao-commit 的边界

- `dao-commit`（`SKILL.md` / `core-protocol.md`）负责**起锚**：什么时机、怎么写 header、`type` 与实际工程行为如何对应。
- 本设计负责**回看与觉知**：锚点积累之后如何自查、如何纠偏、如何回看。
- 二者不互相改写。本设计**不改变**起锚规则（包括"锚点与 `type` 正交、集成边界为门槛"这条当前口径）。

## 13. 下一步待决

1. **纠偏记录落在哪里**：项目内文件（随项目走）还是独立台账？两者各有代价。
2. **② 层版本如何自动获取**：能否在起锚时自动写入 `trigramsVersion`（当前是人工约定）。
3. **"当期自检"的事实侧口径**：哪些指标进、哪些不进（进得越多越像指标，越容易滑向评分）。
4. **是否需要独立的回看记录格式**：还是直接复用 commit footer / 一份 append-only 文件。
5. **验证方式**：至少在一个真实项目连续使用若干轮，观察回看覆盖率与技术债的对应关系。
