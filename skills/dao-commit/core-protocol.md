# Dao Commit 工程协议

> Dao Commit 要解决的，不是"怎么写得像样"，而是"怎么把这一轮真实变化，压成可检索、可回看、可沉淀的高信号锚点"。

---

## 一、格式

```
[上卦下卦][卦名] type(scope): subject

[可选] 背景：
[可选] 判断：
[可选] 停点：
[可选] 踩坑记录：
[可选] 关联经验：
[可选] #沉淀 标题 -> context/experience/example.md
[可选] Refs: / Related: / Closes:
```

### 各段职责

| 部位 | 职责 | 原则 |
|------|------|------|
| `[上卦下卦][卦名]` | 这次变化的 Dao 语义锚点 | 先准后满 |
| `type` | 句法兼容，对接工程生态 | 不担语义主责 |
| `scope` | 主要承载对象 | 不写目录列表 |
| `subject` | **正文重心**，这一轮到底把什么往哪推了一步 | 动词要有力量 |
| `body` | 最少必要上下文 | 能不写就不写 |
| `footer` | 只挂钩，不讲故事 | Refs / Related / #沉淀 |

## 二、卦象：动作 × 承载 → 命名

卦象是语义编码系统，不是装饰。上卦表示动作方向，下卦表示承载对域，卦名为组合后的本质命名。

### 上卦 — 动作方向

| 卦象 | 卦名 | 动作方向 | 含义 |
|------|------|----------|------|
| ☰ | 乾 | 主动创造 | 顶层设计、结构性建设、从零开创 |
| ☱ | 兑 | 开口连接 | 对外表达、暴露接口、建立交互 |
| ☲ | 离 | 照亮可见 | 呈现展示、使状态透明 |
| ☳ | 震 | 启动激活 | 初始化、触发事件、打破平静 |
| ☴ | 巽 | 渗透流动 | 全局漫游、层层推进、深度渗入 |
| ☵ | 坎 | 涉险修复 | 处理风险、谨慎穿越险地 |
| ☶ | 艮 | 止界定边 | 锁定边界、停止扩散、稳定状态 |
| ☷ | 坤 | 承接承载 | 被动实现、容纳支撑、铺底垫基 |

### 下卦 — 承载对域

| 卦象 | 卦名 | 承载对域 | 含义 |
|------|------|----------|------|
| ☰ | 乾 | 核心逻辑层 | 主干业务、核心算法、关键模块 |
| ☷ | 坤 | 基础设施层 | 数据库、存储、OS、网络底座 |
| ☳ | 震 | 事件触发层 | 消息队列、事件系统、定时任务 |
| ☱ | 兑 | 接口连接层 | API、对外交互、支付/接入 |
| ☴ | 巽 | 渗透横切层 | 权限、日志、监控、全局配置 |
| ☵ | 坎 | 高风险通道层 | 安全认证、错误处理、高风险链路 |
| ☶ | 艮 | 配置稳定层 | 环境配置、版本锁定、稳定模块 |
| ☲ | 离 | 展示依赖层 | UI 组件、前端展示、依赖关系 |

### 选卦三步

**第一步：先定下卦** — 这轮变化主要作用在哪个对域？

**第二步：再定上卦** — 这轮动作是什么方向？

**第三步：查表得卦名** — 上卦 + 下卦 组合对应的六十四卦名称。

## 四、subject 写作规则

subject 不写"做了点什么"，写"这一轮到底把什么往哪推了一步"。

### 推荐动词（有方向、有判断、有变化感）

梳理、收束、归位、校准、对齐、补齐、打通、承接、抽出、压平、压降、删去、修复、补入、沉淀、明确、稳住、隔离、统一、归一

### 慎用动词（信息密度低）

优化、调整、更新、完成、处理、修改、支持

### 示例

| 不好 | 好 |
|------|-----|
| `docs(dao): 完善文档` | `docs(dao): 梳理 Dao Commit 与 Conventional Commit 关系` |
| `feat(auth): 更新登录` | `feat(auth): 收束登录链路并补齐异常路径` |
| `refactor(core): 优化代码` | `refactor(core): 抽出公共校验层，统一入参处理` |

## 五、body 最小模板

不是每次都要写。只在 header 不够表达时补。

```
背景：为什么这样动
判断：动到哪、为什么停
停点：这轮收在哪里，后续还差什么
```

---

## 六、footer 规则

footer 不讲故事，只挂钩。

适合放的内容：
- `Refs:` 关联票号
- `Related:` 关联 PR / 文档
- `Closes:` / `Fixes:` 关闭的 Issue
- `#沉淀 标题 -> 路径`
- `归母候选:`

---

## 七、起草顺序

```
❶ 辨真实变化
   这一轮和上一轮相比，哪里真的不一样了？
   如果这条成立，下一步会因此改什么？
   这条能拿现有文档、样本或流程反照吗？

❷ 写 subject
   这一轮到底把什么往哪推了一步？

❸ 定 scope
   这轮变化主要落在谁身上？（不是碰了哪些目录）

❹ 选 type
   feat / fix / refactor / docs / test / chore / style / perf / ci / build
   init / revert / release / deprecate
   只保句法兼容，不担语义主责

❺ 推卦象
   先定下卦（承载对域）→ 再定上卦（动作方向）→ 查表得卦名
   给出 1-2 个候选，不直接给唯一答案

❻ 补 body / footer（按需）
```

> 不要倒过来——先卦象后 subject 容易让 commit 变成"解释文"而不是"锚点"。

## 八、爻位选法（深度模式）

> 卦象是空间坐标（在哪个处境），爻位是时间坐标（在哪个阶段）。选爻是可选的深度模式。
> 爻位首先服务**判断与命名收窄**，不是默认服务展示。

### 爻位含义

同一个卦，不同爻位所处的发展阶段不同。爻位从下往上，代表系统在一个处境中从启动到收束的六个阶段：

| 爻位 | 阶段 | 工程信号 |
|------|------|----------|
| 初爻 | 刚启动 | 方向未定，基础未稳，先搭骨架不急着出功能 |
| 二爻 | 核心跑通 | 小有成果，但还在内部，可以对内展示对齐方向 |
| 三爻 | 过渡危险期 | 新旧并存，进退两难。如果方向不对，revert 比继续推进更好 |
| 四爻 | 进入上层 | 对外暴露或交叉协作，如履薄冰，等待验证 |
| 五爻 | 居中得位 | 协作顺畅，这是处境中最好的位置。小步推进而非冒进 |
| 上爻 | 到顶 | 物极必反，新增复杂度已是纯消耗。该收束、下线、止损 |

### 变卦推导

选定爻位后，计算这一爻动（阳变阴、阴变阳）得到变卦。变卦表示"如果这次提交落地，系统会向哪个方向演化"。

变卦是演化方向提示，不是下一次 commit 的强制卦象。一次提交只走一步本卦→变卦，下次提交重新从上卦下卦开始选。

默认情况下，爻辞原文、工程注、变卦块都**不直接进入 commit message**。它们更适合作为 AI 的内部判断材料，用来帮助：

- 收窄当前阶段判断
- 调整 subject 的语气强弱
- 缩小 type 候选范围
- 提醒这次提交更像启动、迁移、发布、收口，还是终止

### commitHint 优先级

爻位被选定时，commit type 以爻位建议优先，卦层 `suggestedType` 降为 fallback。commitHint 是建议收窄，不强制覆盖——用户可以在看到建议后自行选择。

### 当前状态

爻位数据正在逐步建设中。当前已录入：**屯卦 6 爻**。其他卦的爻位数据将在后续迭代中补入。

当前工程目标不是把 Dao Commit 做成"易经展示器"，而是先让它在真实开发场景里更能判断、更会命名、更少跑偏。

## 九、何时使用 Dao Commit

Dao Commit 不替代 Conventional Commit，不是每次提交都要用。

**应该用 Dao Commit 的时刻：**
- Milestone 完成，阶段性收口
- Squash merge 到 `main` 分支，准备发布
- 系统发生本质变化（架构切换、方向调整、重要里程碑）
- 一次值得未来回头看的变化

**不应使用 Dao Commit 的时刻：**
- 日常 feat/fix/chore 类提交——用普通 Conventional Commit
- 小范围修改、格式调整、临时修复
- 中间状态的 WIP 提交

> Dao Commit 是锚点，不是格式。只在值得命名的时刻使用。用多了反而增加噪音。
