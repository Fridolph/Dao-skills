# Dao Commit 工程协议

> Dao Commit 要解决的，不是"怎么写得像样"，而是"怎么把这一轮真实变化，压成可检索、可回看、可沉淀的高信号锚点"。

---

## 一、格式

```
[上卦下卦][卦名] type(scope): subject

[可选] 背景：
[可选] 判断：
[可选] 停点：
[可选] 踩坑记录：
[可选] 关联经验：
[可选] #沉淀 标题 -> context/experience/example.md
[可选] Refs: / Related: / Closes:
```

### 各段职责

| 部位 | 职责 | 原则 |
|------|------|------|
| `[上卦下卦][卦名]` | 这次变化的 Dao 语义锚点 | 先准后满 |
| `type` | 句法兼容，对接工程生态 | 不担语义主责 |
| `scope` | 主要承载对象 | 不写目录列表 |
| `subject` | **正文重心**，这一轮到底把什么往哪推了一步 | 动词要有力量 |
| `body` | 最少必要上下文 | 能不写就不写 |
| `footer` | 只挂钩，不讲故事 | Refs / Related / #沉淀 |

---

## 二、卦象：整体处境 → 命名

卦象是语义编码系统，不是装饰，也不是“动作 × 承载”的机械组合。六十四卦先描述本次集成单元所处的整体局面，以及净变化对该局面的意义；`type` 只记录具体工程行为。

### 选卦四步

1. **先定集成单元与相对基线**：只为跨过集成边界后成立的净变化命名。
2. **写出整体处境**：先不用卦名，描述什么关系、风险、秩序、条件或过门发生了改变。
3. **用选择检查筛选并近义复核**：读取 `references/64卦选择检查.md`，候选必须满足必要条件，并至少说明一个近义卦为何不取；证据不足时不强定。
4. **最后解释上下卦**：选定卦名后，从 `trigrams.json` 读取既定符号，作为结构解释与 header 标识；不得由模块、动作或符号反推卦名。

`trigrams.json` 保留卦象结构、经典/工程参考、场景警示与允许的 Conventional Commit type，但不承担机械卦名推荐。完整选择检查见 `references/64卦选择检查.md`。

---

## 三、选择检查与卦象标识

- `references/64卦选择检查.md`：运行时权威，记录每卦的必要条件与关键近义分界。
- `trigrams.json`：记录卦名、既定上下卦符号、经典/工程参考与允许的 Conventional Commit type；参考内容不绑定 type。
- 母仓候选册：保存经典锚点、工程适配、反适配与后续真实样本反照，不替代运行时最小索引。

## 四、subject 写作规则

subject 不写"做了点什么"，写"这一轮到底把什么往哪推了一步"。

### 推荐动词（有方向、有判断、有变化感）

梳理、收束、归位、校准、对齐、补齐、打通、承接、抽出、压平、压降、删去、修复、补入、沉淀、明确、稳住、隔离、统一、归一

### 慎用动词（信息密度低）

优化、调整、更新、完成、处理、修改、支持

### 示例

| 不好 | 好 |
|------|-----|
| `docs(dao): 完善文档` | `docs(dao): 梳理 Dao Commit 与 Conventional Commit 关系` |
| `feat(auth): 更新登录` | `feat(auth): 收束登录链路并补齐异常路径` |
| `refactor(core): 优化代码` | `refactor(core): 抽出公共校验层，统一入参处理` |

---

## 五、body 最小模板

不是每次都要写。只在 header 不够表达时补。

```
背景：为什么这样动
判断：动到哪、为什么停
停点：这轮收在哪里，后续还差什么
```

---

## 六、footer 规则

footer 不讲故事，只挂钩。

适合放的内容：
- `Refs:` 关联票号
- `Related:` 关联 PR / 文档
- `Closes:` / `Fixes:` 关闭的 Issue
- `#沉淀 标题 -> 路径`
- `归母候选:`

---

## 七、起草顺序

```
❶ 辨真实变化
   这一轮和上一轮相比，哪里真的不一样了？
   如果这条成立，下一步会因此改什么？
   这条能拿现有文档、样本或流程反照吗？

❷ 写 subject
   这一轮到底把什么往哪推了一步？

❸ 定 scope
   这轮变化主要落在谁身上？（不是碰了哪些目录）

❹ 选 type
   feat / fix / refactor / docs / test / chore / style / perf / ci / build
   init / revert / release / deprecate
   只保句法兼容，不担语义主责

❺ 选卦象
   先写整体处境 → 选择检查筛选 → 近义卦复核 → 最后解释上下卦
   给出 1-2 个候选，不直接给唯一答案；证据不足时不强定

❻ 补 body / footer（按需）
```

> 不要倒过来——先卦象后 subject 容易让 commit 变成"解释文"而不是"锚点"。

## 八、爻位选法（深度模式）

> 卦象是空间坐标（在哪个处境），爻位是时间坐标（在哪个阶段）。选爻是可选的深度模式。
> 爻位首先服务**判断与命名收窄**，不是默认服务展示。

### 爻位含义

同一个卦，不同爻位所处的发展阶段不同。爻位从下往上，代表系统在一个处境中从启动到收束的六个阶段：

| 爻位 | 阶段 | 工程信号 |
|------|------|----------|
| 初爻 | 刚启动 | 方向未定，基础未稳，先搭骨架不急着出功能 |
| 二爻 | 核心跑通 | 小有成果，但还在内部，可以对内展示对齐方向 |
| 三爻 | 过渡危险期 | 新旧并存，进退两难。如果方向不对，revert 比继续推进更好 |
| 四爻 | 进入上层 | 对外暴露或交叉协作，如履薄冰，等待验证 |
| 五爻 | 居中得位 | 协作顺畅，这是处境中最好的位置。小步推进而非冒进 |
| 上爻 | 到顶 | 物极必反，新增复杂度已是纯消耗。该收束、下线、止损 |

### 变卦推导

选定爻位后，计算这一爻动（阳变阴、阴变阳）得到变卦。变卦表示"如果这次提交落地，系统会向哪个方向演化"。

变卦是演化方向提示，不是下一次 commit 的强制卦象。一次提交只走一步本卦→变卦，下次提交重新从整体处境开始选。

默认情况下，爻辞原文、工程注、变卦块都**不直接进入 commit message**。它们更适合作为 AI 的内部判断材料，用来帮助：

- 收窄当前阶段判断
- 调整 subject 的语气强弱
- 缩小 type 候选范围
- 提醒这次提交更像启动、迁移、发布、收口，还是终止

### type 边界

`type` 始终按本次净变化的具体工程行为选择。卦象和爻位都只帮助理解系统处境、阶段与命名口气，不生成或覆盖 `type`。

### 当前状态

爻位数据正在逐步建设中。当前已录入：**屯卦 6 爻**。其他卦的爻位数据将在后续迭代中补入。

当前工程目标不是把 Dao Commit 做成"易经展示器"，而是先让它在真实开发场景里更能判断、更会命名、更少跑偏。

## 九、何时使用 Dao Commit

Dao Commit 不替代 Conventional Commit，也不为每次任务收口单独起卦。

**应该用 Dao Commit 的时刻：**
- 多笔普通提交在 `feature -> dev` 合并 / squash 后形成净变化
- `dev -> main` 合并 / squash 前，出现值得长期回看的明确净差异

**不应使用 Dao Commit 的时刻：**
- 日常开发、流程修订或单任务收口——用普通 Conventional Commit
- 尚未跨过集成边界、未形成净变化的零散修改、格式调整与中间状态
- WIP 提交

> **锚点与 `type` 正交。** 一次全是老问题修复的发布，`type` 以 `fix` 为主；一次以结构整理为主的集成，`type` 就是 `refactor`——没有新功能不影响它是否值得起卦。这里排除的是**未跨过集成边界的零散提交**，不是某类 `type`。

> Dao Commit 是锚点，不是格式。只在值得命名的时刻使用。用多了反而增加噪音。
