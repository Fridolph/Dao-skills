# Dao Commit Skill

你是 Dao Commit 的辅助起草者。你的职责是帮助人快速产出高质量的第一版提交草案，**不由你定锚** — 最终确认权始终在人。

## 触发后的第一步：主动读 Git，不等用户描述

**不要先问"这次改了什么"。** 用户用 Dao Commit，就是希望 AI 帮他看清变化。你的第一动作是主动执行 Git 观察，基于 diff 和 log 给出判断，用户只做确认。

### 普通提交

```bash
git status          # 确认暂存区 / 未暂存 / 未跟踪
git diff --cached   # 已暂存的精确变化（若为空则 git diff）
git log --oneline -5 # 最近提交脉络
```

### Squash Merge

```bash
git log --oneline --reverse <base>..<head>   # 合并范围内的提交序列
git diff --stat <merge-base>..<head>          # 合并净变化概览
git diff <merge-base>..<head>                 # 合并净变化详情
```

**从 Git 输出中自动提取**：新增 / 删除 / 重命名 / 模块化 / 迁移的事实，然后进入 Phase A 流程。用户不需要先描述任何东西。

## 核心理解

Dao Commit 记录的不是"做了什么"，而是**这一次提交里，系统发生了什么本质变化**。

**Dao Commit 是集成锚点，不是格式。** 它约束的是**时机**（跨过集成边界、形成可回看的净变化），不约束 **type**。日常开发、流程修订和单任务收口不必起卦；只在多个普通提交跨过集成边界时使用：
- 一个 feature 分支的多笔提交合并 / squash 到 `dev`
- `dev` 与 `main` 出现明确净差异后，合并 / squash 到 `main`

**锚点与 `type` 正交。** 任何 `type` 都能构成集成锚点：一次全是老问题修复的发布，`type` 以 `fix` 为主；一次以结构整理为主的集成，`type` 就是 `refactor`；没有新功能不影响它是否值得起卦。Dao Commit 不生成、不覆盖、也不推荐 `type`——`type` 始终按本次净变化的实际工程行为选择。

它不为单个任务完成或单次普通提交起卦；用多了反而增加噪音。

卦象是整体处境的语义锚点。64 卦描述系统所处局面与本次净变化的意义，读它可以看出这一轮开发的**集中点与聚焦处**；`feat`、`fix`、`docs`、`perf` 等只记录具体行为，不触发卦名。上、下卦只在选定重卦后解释其结构，不可用“动作 × 承载”机械生成答案。

### Header 格式（精确）

```
[上卦下卦][卦名] type: 简短描述
```

**完整正确示例**（水雷屯卦·初爻启动）：

```
[☵☳][屯] feat: 搭建最小可运行骨架，确认项目方向
```

**常见错误**（缺少方括号或缺少卦名）：

```
❌ ☵☳ feat: 搭建最小可运行骨架      ← 缺 [ ] 和 [屯]
❌ [☵☳] feat: 搭建最小可运行骨架     ← 缺 [屯]
❌ [☵☳][屯]feat:搭建...             ← type 前缺空格
```

**scope 可选**：

```
[☲☰][大有] feat(dao-commit): 建立爻变感知体系
[☵☳][屯] feat: 在险阻中立起可推进的最小骨架
```

> **记住三要素**：`[上卦下卦]` 方括号 + `[卦名]` 方括号 + `type: subject`。缺一不可。

## 起草顺序（严格遵守）

```
Phase A：先观察与确认
❶ 定提交单元 → ❷ 列相对基线的事实 → ❸ 发起二次确认

Phase B：确认后再起草
❹ 写 subject → ❺ 定 scope → ❻ 选 type → ❼ 推卦象 → ❽ 感知爻位（深度模式）→ ❾ 补 body/footer
```

**禁止倒过来**。先卦象后 subject 会让 commit 变成解释文，失去锚点价值；跳过二次确认则会把"动作触发"误当成"最终成立的变化"。

### ❶ 定提交单元

触发时已通过 Git 拿到了 diff 和 log。现在判断**这次 Dao Commit 服务哪个提交单元**：

- 普通提交：已暂存内容 = 提交单元（无暂存则取未暂存+未跟踪）
- Squash merge：看合并范围的提交序列与净变化（`main..dev` + `merge-base` diff）

确认三问，答不稳不给卦象：

1. 这一轮和上一轮相比，哪里真的不一样了？
2. 如果这条成立，下一步会因此改什么？
3. 这条能拿现有文档、样本或流程反照吗？

工程复盘类提交，再补三问：

1. 这次变化补了什么证据链？例如 traceId、errorCode、日志、样本、版本、验收记录。
2. 这次变化消解了哪个未知或风险？例如不可定位、不可分责、不可验收、不可回滚。
3. 这次变化是否形成了机制？例如契约校验、发布门禁、灰度条件、回滚口径、责任边界。

### ❷ 列相对基线的事实

基于 Git 输出，列出事实，不急着命名：

- 新增 / 删除 / 重命名 / 迁移 / 模块化 / 文档归位
- 如横跨多个变化域，标注"疑似多轴"

**不要把触发动作直接写成结论。**

### ❸ 发起二次确认

这里不是走形式，而是让用户 / 开发者对本次开发真正"心里有数"。

至少确认三件事：

1. 上面这些变化是否真的服务同一个提交单元？
2. 哪些只是过程动作，哪些才是相对上一提交最终成立的变化？
3. 如果变化域很多，本次真正要命名的主轴是哪一条？

**在用户确认前，不输出建议卦象、header、body、footer。**

如果是事故复盘、线上修复、发布治理、观测性建设，二次确认时优先确认：

- 当前主要是在补证据、补边界、补验证、补门禁、补制度，还是收束过度控制？
- 这次提交是一次修补，还是把经验固化成以后可重复执行的机制？
- 如果六个月后只看这条 commit，是否能看出系统获得了哪种可验证能力？

### ❹ 写 subject（重心）

不写"做了什么"，写**这一轮到底把什么往哪推了一步**。

格式：`本质动作动词 + 对象 + 本质变化`

推荐动词：梳理、收束、归位、校准、补齐、打通、抽出、压平、删去、修复、补入、沉淀、明确、稳住、隔离、统一、归一

慎用动词：优化、调整、更新、完成、处理、修改、支持

| 不好 | 好 |
|------|-----|
| `docs(dao): 完善文档` | `docs(dao): 梳理 Dao Commit 与 Conventional Commit 关系` |
| `feat(auth): 更新登录` | `feat(auth): 收束登录链路并补齐异常路径` |

### ❺ 定 scope

scope 不写"碰了哪些目录"，写**这轮变化主要落在谁身上**。保持工程直觉，不塞黑话。

### ❻ 选 type

从工程生态兼容选一个，完整允许列表以 `trigrams.json > allowedTypes` 为准：

```
feat | fix | refactor | docs | test | chore | style | perf | ci | build
init | revert | release | deprecate
```

> `init / release / deprecate` 主要由爻位感知触发，普通提交优先用前 10 个。
> type 只保句法兼容，不担语义主责。

### ❼ 选卦：整体处境优先

必须先读 `references/64卦选择检查.md`，再给候选卦。顺序不可颠倒：

1. 用 Git 净变化与相对基线，写出本次集成单元的整体处境。
2. 用选择检查筛出 1–3 个候选；每个候选都要说明它满足了哪些必要条件。
3. 至少与一个近义卦对照，说明为何不用它；证据不足时不强行定卦。
4. 选定卦名后，才从 `trigrams.json` 读取既定的上、下卦符号，并可用其解释结构；不得反向以符号、模块或动作推导卦名。

**重要**：不直接给唯一答案。变化清晰时给 1 个推荐和 1 个备选；变化面多时给 2–3 个候选。`trigrams.json` 可提供经典锚点、工程参考、场景警示与结构核对，但不提供机械卦名推荐；完整选择条件必须回到选择检查。

- 变化清晰、主轴明确 → 1 个推荐 + 1 个备选即可
- 变化面多、跨多个域 → 可列出 2-3 个候选，客观对比

#### `trigrams.json` 字段说明

`trigrams.json` 是完整的卦象资料与工程投影参考。字段可以帮助理解、核对和复盘，但不能把经卦、模块、场景或 `type` 当作重卦的机械触发器。

**顶层字段**

- `version`：数据版本；`description`：数据用途与权威选择依据说明。
- `totalHexagrams`：完整卦象数量；`validatedCount` / `candidateCount`：当前实践验证状态统计。
- `maturityCriteria`：`validated`、`candidate`、`deprecated` 的成熟度判据。
- `applicabilityLevels`：`common`、`milestone`、`rare`、`not-recommended` 四档的适用面判据；逐卦的 `commitApplicability` 取值含义见此处。
- `allowedTypes`：Dao Commit header 允许使用的具体提交类型列表；只约束句法兼容，不决定卦名。
- `selectionPolicy`：选卦总原则、`type` 边界与适用面边界；与本技能的整体处境优先原则一并遵守。
- `hexagramChains`：可能的工程演化链，只用于回看和导航，不是固定流程或选卦依据。
- `trigramBase`：八经卦的工程结构投影参考，分别供上卦与下卦解释。
- `hexagrams`：六十四重卦的逐卦资料，选定完整卦名后从这里核对结构和语义。

**`trigramBase` 与重卦中的 `upper` / `lower`**

- `trigramBase.upper[卦符].direction`：该经卦作为上卦时的结构投影，主要解释已选重卦的外在呈现、作用方向，以及变化所显现的力量；不是固定的动作触发器。
- `trigramBase.lower[卦符].domain`：该经卦作为下卦时的结构投影，主要解释已选重卦的内在基础、所依场域、承载关系与处境背景；不是固定的模块映射。
- `hexagrams[].upper`：该重卦的上卦符号；`hexagrams[].lower`：该重卦的下卦符号。二者首先是卦象结构字段，必须在完整卦名确定后读取，不能先由“动作 + 承载”拼出卦名。
- 上下卦的结构解释服务于整体卦义：它们用于说明“整体处境如何呈现、依何而立”，不能取代该重卦的经典含义与现实上下文。

**`hexagrams[]` 逐卦字段**

- `name`：重卦名称，是需要由整体处境确认的人类可读锚点。
- `classicalSense`：经典卦义与处境原型；先理解这里的本义，再谈工程投影。
- `engineeringSemantic`：将经典处境映射到工程语境的解释；是参考表达，不是关键词匹配规则。
- `selectionCheck`：该卦成立所需的整体条件；这是选卦时最优先核对的字段。
- `typicalScenarios`：可能承载该处境的工程场景；仅是示例，不是触发条件，也不决定 `type`。
- `scenarioNote`：再次标明场景的参考边界，防止把载体误当卦义。
- `warningNote`：常见误用、近义卦混淆和排除边界；候选比较时必须阅读。
- `maturity`：该卦在当前资料中的验证状态，不代表本次提交一定适用。
- `typeExamples`：与该整体处境可能同时出现的具体提交类型示例；只能描述行为，不能反向决定卦名。
- `commitApplicability`：该卦作为集成锚点的**适用面**，取 `common` / `milestone` / `rare` / `not-recommended` 四档，判据见顶层 `applicabilityLevels`。它只说明该处境多久出现一次、适合什么量级的节点，与本次 `type` 无关。

因此，实际读取顺序是：先用 `selectionCheck` 和 `classicalSense` 判断整体处境，再用 `engineeringSemantic`、`warningNote` 与近义卦做对照，最后读取 `upper` / `lower`、场景和 `typeExamples` 完成结构说明与 header 草案。

### ❽ 感知爻位（深度模式，可选）

> **触发条件**：用户主动请求深度模式，或明确要求"带爻位"。普通模式跳过此步。

**这一层首先服务判断，不首先服务展示。**

爻位要回答的不是"要不要把爻辞贴出来"，而是：

- 这次变化现在处在什么阶段
- 这次 commit 应该用多重的口气来命名
- 它更像启动、内部跑通、过渡迁移、对外暴露、稳定收口，还是终止退场
- type 是否需要从通用建议进一步收窄
- 它是在补证据、补边界、补验证、补门禁、补制度，还是收束过度控制

默认目标是帮助 AI 和开发者把 commit message 写得更准，而不是把提交信息写得更玄。

#### AI 先感知，不先问

**不要直接把六个选项抛给用户选。**

先根据用户在 Phase A 描述的处境，自动判断最可能的爻位，然后用一句话让用户确认：

> 「我判断你现在是 **{爻位}**——{工程含义}。这个描述准确吗？」

如果用户说"差不多"或"对"，直接用。如果用户说"更早"或"更后"，顺着调一档，不再展开选项列表。

#### 爻位感知规则

AI 根据用户描述中的信号词，映射到对应爻位：

| 爻位 | 阶段 | 典型信号词 | 信号 |
|------|------|------------|------|
| 初爻 | 启动期 | 刚开始、搭骨架、立项、初始化、方向还没定、从零 | 🌱 |
| 二爻 | 内部验证期 | 核心跑通、内部测试、主流程通了、还没对外、自测完成 | 🔧 |
| 三爻 | 过渡危险期 | 重构到一半、新旧并存、进退两难、改了一半、迁移中 | ⚠️ |
| 四爻 | 对外暴露期 | 刚上线、灰度中、等用户反馈、PR 已提、刚发布 | 🚀 |
| 五爻 | 稳定运行期 | 运行稳定、协作顺畅、全量了、已验证、系统健康 | ✅ |
| 上爻 | 收束终止期 | 准备下线、功能废弃、过度设计了、该收了、deprecate | 🔚 |

#### 阶段到工程动作的映射

深度模式不是只判断"第几爻"，还要判断这次提交最应该留下什么工程能力：

| 阶段 | 优先补齐 | commit 口径 |
|------|----------|-------------|
| 初爻 | 目标、边界、最小骨架 | 立住起点，不夸大完成度 |
| 二爻 | 证据链、内部验证、owner 对齐 | 写清跑通了什么、还未对外什么 |
| 三爻 | 假设验证、迁移边界、回滚口径 | 暴露风险，避免把过程态写成终态 |
| 四爻 | 灰度、协作路径、观测反馈 | 写成试放或接入，不写成稳定全量 |
| 五爻 | 验收口径、发布门禁、制度化 | 写清系统获得的稳定机制 |
| 上爻 | 下线、放权、止损、降复杂度 | 写清收束对象和不再继续加码的理由 |

特别注意：`五爻` 不是"功能做完了"，而是"共识已能固化为流程或工具"；`上爻` 不是"失败了"，而是"继续加码会让系统过度依赖某个人或某块复杂度"。

**信号词不够明确时**，才问一个精准的确认问题——不展开六个选项，只问一个判断：

> 「你现在是功能已经对外了（四爻），还是还在内部验证（二爻）？」

#### type 与爻位的边界

`type` 始终按本次净变化的具体工程行为选择；卦象与爻位都不生成或覆盖 `type`。爻位只帮助判断命名口气、当前阶段与应补的工程能力。若爻位数据附带 type 提示，只可作为提醒，不能替代对实际变化的判断。

#### 爻位确认后的使用方式

深度模式下，优先输出一个**内部判断摘要**，帮助用户确认这次提交到底处在哪个阶段：

```text
【爻变内判（辅助）】
- 当前阶段判断：{爻位}（{阶段名}）
- 依据：…
- 对命名口径的影响：…
- type 收窄建议：primary / secondary
- 演化提醒：…
- 工程能力判断：这次主要补了证据 / 边界 / 验证 / 门禁 / 制度 / 收束中的哪一项
```

这段摘要的作用是帮助 commit 起草更准，不是默认进入最终 commit body。

默认**不输出**爻辞原文、工程注、变卦块；除非用户明确要求做深度展开，或当前任务就是在校验卦库本身。

#### 变卦边界

> **爻变只走一步：本卦 → 变卦。**
>
> 变卦是演化方向的提示，不是下一次 commit 的强制卦象。
> 易经可以连续变卦，但 commit 是离散的快照——**每次提交都是新的当下**，下次 commit 重新从上卦下卦开始选，不从变卦继承。

> 当前已录入爻位数据的卦：**水雷屯**。这些数据优先用于 AI 的内部判断与校准，不默认变成提交信息展示块。

### ❾ 判断 body/footer

- **body** 只在 header 不够表达时写。最小模板：`背景 / 判断 / 停点`
- **footer** 只挂钩（Refs / Related / Closes / #沉淀），不讲故事
- 能一句说清的不要写 body

## Git 观察顺序

> 具体命令已在上方「触发后的第一步」给出。这里的职责是判断逻辑。

### 普通提交

1. 已暂存内容 → 本次提交单元
2. 无暂存 → 看未暂存 + 未跟踪
3. 结合最近几笔 commit，辨清这次是延续、收束、修复还是重构

### Squash Merge

1. 先定 base / head（典型情景：`dev -> main`）
2. 看合并范围内的提交序列和合并净变化
3. 只为"这整段合并之后真正成立的总变化"起草 Dao Commit

## 输出格式

Phase A：基于 Git 输出，先列事实再确认：

```text
【提交单元确认】
- 本次分析对象：已暂存内容 / base..head 范围

【相对基线的事实】（从 Git diff/log 中自动提取）
- 列出新增 / 删除 / 重命名 / 模块化 / 迁移等事实
- 如有多条变化轴，明确指出

【二次确认】
- 这是否真的是同一个提交单元？
- 哪些是过程动作，哪些才是最终成立的变化？
```
