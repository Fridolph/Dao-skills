# Dao Review

## 这份说明是做什么的

`dao-review` 是一份“收口前检查说明”。

它不替代代码 review，也不替代测试。
它要做的是一件更具体的事：

> 在准备收口之前，先判断这一轮到底能不能交付。

它最核心的问题是：

> 这轮现在是真的可以往 `review-ready / done` 走，还是其实还差一门；收口后该走常规提交，还是正处于需要 Dao Commit 的集成边界？

## 什么时候进入这份说明

当问题的核心不是“怎么实现”，而是“现在能不能收”时，进入这份说明。

典型触发语气包括：

- “这轮你帮我 review 一下能不能收口。”
- “我觉得差不多了，你帮我看是否 ready。”
- “自测完了，下一步该普通提交还是走 Dao Commit？”
- “这轮现在算不算 done？”
- “帮我看下还有没有隐藏风险。”

更强的触发信号包括：

- 一轮实现已基本完成
- 自测已做或计划做完
- 准备交给下一位 review
- 准备合并 / squash，需判断是否形成集成锚点
- 用户感觉“差不多”，但还没正式收口

## 什么时候不要进入这份说明

如果当前还在需求对齐，不要用 `dao-review`。

如果当前还在交接中断续跑，也不要用 `dao-review`。

不要用于：

- 新任务开工
- 任务身份归位
- 归母判断
- 普通代码实现中途

如果真正的问题是：

> 这轮现在能不能开做？

那更接近 `dao-grill`。

如果真正的问题是：

> 现在换人接，怎么不断棒？

那更接近 `dao-handoff`。

## 核心判断

`dao-review` 主属 `L4`，连接 `L2` 与 `L3`。

它先守一句：

> 不是看“像不像完成了”，而是看“有没有真正过门”。

当前最小先看 7 类问题：

1. 是否符合目标
2. 是否越界
3. 是否完成自测
4. 是否有隐藏风险
5. 是否需要补文档
6. 收口后的提交路径
7. 是否产生沉淀候选

## 使用顺序

### 第一步：先回这轮开工时的目标

先对照：

- 这轮最初要成立的是什么
- 当时明确不做什么
- 现在是否已经偏出原边界

不要脱离起点空谈“看起来做了很多”。

### 第二步：只看本轮，不替下一轮背锅

`dao-review` 看的是：

- 这一轮是否过门

不是：

- 整个项目是否已经完美
- 以后还有没有更多事能做

### 第三步：自测要看证据，不看语气

不要接受：

- “我觉得应该没问题”
- “大概跑过了”
- “理论上可以”

要交清：

- 做了什么自测
- 没做什么
- 风险还剩在哪

### 第四步：风险写实，不写安慰

如果存在这些情况，要明确指出：

- 功能通了，但没验证边界
- 核心改了，但没看回归影响
- 文档缺口会让下一位难接
- 这轮还不足以收口或提交

### 第五步：给出明确收口结论

结论只给三种：

- `可收口`
- `需补一项`
- `暂不建议收口`

不要只给模糊建议。

## 输出原则

### 1. Findings 先于总结

如果发现问题，先列问题，再说整体判断。

### 2. 风险按严重度排

优先指出：

- 会导致误收口的问题
- 会让下一位误判的问题
- 位于集成边界时，会让 Dao Commit 锚错的问题

### 3. 通过也要写清剩余边界

即使判断可以收口，也要说明：

- 这是在什么边界内成立
- 哪些后续工作不属于本轮

### 4. Dao Commit 不是日常收口的自动附赠

日常开发、流程修订与单任务收口，使用 Conventional Commit。
只有多个普通提交在 `feature -> dev` 或 `dev -> main` 合并 / squash 后，形成值得长期回看的净变化时，才建议进入 `Dao Commit`。

## 标准输出形状

### 1. 当前总判断

先给一句话判断：

- `这轮可以收口`
- `这轮只差一项`
- `这轮现在还不适合收口`

### 2. 关键发现

按优先级列出发现。

### 3. Dao Review Card

```text
是否符合目标：
是否越界：
是否完成自测：
是否有隐藏风险：
是否需要补文档：
提交路径：`常规提交 / 集成 Dao Commit / 暂缓`
是否产生沉淀候选：
```

### 4. 收口结论

结论只给三种：

- `可收口`
- `需补一项`
- `暂不建议收口`
