# Dao 与 Dao-is-Coding

## 一句话定位

`Dao` 是母体；`Dao-is-Coding` 是以 Dao 为根的 AI Native 架构、协作与编程范式，也是它在软件工程中的第一条核心验证线。

这里的重点不只是让 AI 多写一些代码，而是让软件生产过程中的判断、边界、验证、交接和经验，能被人和 AI 一起看见。

## 它试图解决什么

AI 可以快速生成代码，却也会放大几类长期存在的问题：

- 目标尚未清楚，已经开始高效实现错误的东西。
- 决策散在对话和人脑里，换人、换窗口、换模型就断。
- 自测、review、合并和提交之间缺少明确的过门条件。
- 提交只记录动作，半年后难以理解系统到底变成了什么。
- 项目里长出的经验要么丢失，要么过早被抬成全局规则。

`Dao-is-Coding` 当前不承诺消灭这些黑盒；它更务实的目标是：通过持续判断与持续验证，让黑盒逐步变小。

## 六层不是线性工序

| 层 | 当前职责 | 最短记忆 |
| --- | --- | --- |
| `L1` | 根命题、愿景与真实承载 | 为什么做、是否仍在主线 |
| `L2` | 过门判断、原则与边界 | 能不能过、还差什么 |
| `L3` | 语义锚点与年轮 | 这轮真实变化叫什么 |
| `L4` | 任务流转、交接与收口 | 现在在哪、下一棒怎么接 |
| `L5` | 知识沉淀 | 哪些经验值得留下 |
| `L6` | 传播与演进 | 如何让外部理解和参与 |

它们不是“需求 -> 设计 -> 开发”的替代流水线。真实现场更接近：

```text
L1 持续校根
L4 持续流转
L2 按需过门
L3 到点留锚
L5 / L6 按成熟度沉淀与表达
```

## 与经典工程方法的关系

`SOLID`、`DRY`、`KISS`、Unix 哲学、测试、Git 与 PR 都不是被替换的对象。它们是成熟的局部工具和原则。

`Dao-is-Coding` 要做的是在当前处境中判断：哪一个原则此刻该出场、边界放在哪里、怎样验证、如何交接，以及经验何时足以跨出项目上下文。易经或奇门的映射可以帮助人和 AI 看见结构，但工程事实始终优先：映射是镜子，不是裁判。

## 当前阶段的承诺

先在真实项目中跑通最小闭环，再把反复成立的部分提炼为可迁移的协议、模板与工具。不要因为它有完整叙事，就误认为已经完成验证。
