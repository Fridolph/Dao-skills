# 复杂模块组织法

这是在真实报价业务重构中已使用并跑通的局部工程方法。它适用于状态、触发、计算路径与响应式副作用开始缠绕的复杂模块，不是所有代码都要套的框架。

工程上真正要守的是：

> 先排清状态、触发、输出、场景、规则与写入边界，再开始落代码。

## 何时值得起盘

当出现以下组合时，建议在实现前先做一次起盘：

- 多个状态互相联动，存在派生值或写入顺序。
- 外部数据、用户输入、系统事件共同驱动模块。
- 同一业务同时有正向计算、逆向推算、初始化或兼容路径。
- 单一入口混进聚合、计算、路由、写入和监听。
- 多个场景需要交付同一稳定结果结构。

简单展示、单一输入输出或普通函数拆分已经足够清楚时，不要为了完整而增加层次。

## 起盘六问

| 问题 | 先看什么 | 最小产物 |
| --- | --- | --- |
| 地盘 | 核心状态、默认值、所有者、不变量 | 状态清单；区分输入、派生、输出 |
| 时干 | 外部数据、用户输入、系统事件 | 触发清单或 `TriggerType` |
| 输出 | 模块最终交付的契约 | 稳定的 `OutputType` / 内部结果类型 |
| 场景 | 正向、逆向、初始化、联动、兜底 | 显式路由与单一职责场景函数 |
| 原子规则 | 哪些领域知识不能多处解释 | 可单测的纯函数 |
| 监听与归位 | 何处触发、何处写入、防循环 | 集中的监听层与明确写入点 |

九个核心状态、二十行调度器、四十行场景函数都只是复查信号，不是强制数字。真正验收是维护者能否解释每个状态、每条路径和每次写入的责任归属。

## 推荐组织顺序

```ts
// 内部类型：_XxxSnapshot / _XxxResult
// 状态骨架：ref、setter、不变量
// 只读派生：computed
// 调度入口：只编排，不承载领域公式
// 快照聚合：_buildXxx()
// 场景路由：_resolveXxx()
// 场景函数：_gateXxx()
// 原子规则：_atomXxx()
// 结果归位：_applyXxx()
// 监听层：watch 与循环保护
// 对外 API：return
```

建议的命名契约：

- `_build*` 聚合或构建数据。
- `_resolve*` 路由或决策。
- `_gate*` 一条业务场景。
- `_atom*` 一条无副作用领域规则。
- `_apply*` 计算结果的统一归位。
- `set*` 明确拥有者的状态写入；`get*` / `orchestrate*` 主动获取或编排。

奇门术语如“地盘、时干、值符、值使”只是共同记忆支架；代码命名始终优先服务项目维护者。映射不能替代工程证明。

## 与 Dao Flow 的接法

```text
目标或边界不清 -> dao-grill
-> L2 判断复杂度是否值得起盘
-> 起盘六问
-> 实现与局部测试
-> dao-review 检查职责、触发、写入与边界
-> dao-commit 为真实结构变化定锚（按需）
```

重构验收至少覆盖：行为等价样本、外部回填/用户输入/模式切换等触发矩阵、循环与覆盖风险、边界输入和历史兼容。结构更整齐不等于领域规则自然正确。

## 最小起盘卡

```md

场景：正向 / 逆向 / 初始化 / 兜底：

```
