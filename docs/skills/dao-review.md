# `dao-review`：收口前过门

`dao-review` 在实现与自测之后，判断当前这一轮是否真的可以交付。它不替代代码 review、测试或 CI；它要求把这些活动留下的证据带回到本轮目标、边界与风险中，给出明确的收口结论。

## 何时使用

- 一轮实现基本完成，准备交给下一位 review。
- 自测已完成或正在补齐，想判断是否仍有一门没有过。
- 准备提交、合并或 squash，需要分清常规提交与集成 Dao Commit。
- 团队感觉“差不多了”，但尚未有可交付的结论。

## 它检查什么

| 检查项 | 要回答的问题 |
| --- | --- |
| 目标 | 本轮最初要成立的事是否已经成立？ |
| 边界 | 是否做进了本轮明确不做的内容？ |
| 自测 | 做了哪些验证、没做哪些验证？ |
| 风险 | 是否仍有回归、兼容、交接或未知风险？ |
| 文档 | 下一位是否会因缺少说明而误判？ |
| 提交路径 | 应走常规提交、集成 Dao Commit，还是暂缓？ |
| 沉淀 | 是否出现值得观察或归母的经验？ |

## 三种结论

`dao-review` 只给出一种明确结论：

- **可收口**：在本轮边界内已经成立，证据与剩余边界已交清。
- **需补一项**：主线基本成立，但有一个明确缺口阻止收口。
- **暂不建议收口**：目标、自测或风险仍不足以支持交付。

## 提交路径

日常开发、流程修订和单任务收口使用 Conventional Commit。只有多个普通提交在 `feature -> dev` 或 `dev -> main` 合并 / squash 后，形成值得长期回看的净变化，才建议进入 [`dao-commit`](dao-commit.md)。

这意味着“改动很大”或“任务完成了”本身都不是起卦条件。

## 最小使用示例

```text
订单导出已实现并完成本地测试。请用 dao-review 检查：
是否符合原目标、是否越界、测试证据是否足够、是否需要补文档；
并明确告诉我应常规提交、走集成 Dao Commit，还是暂缓。
```

## 它不会替代什么

- 不负责发现所有代码缺陷；仍需代码 review、测试、静态检查和 CI。
- 不替下一轮任务背锅；它只判断本轮是否过门。
- 不因“完成感”自动要求 Dao Commit。
