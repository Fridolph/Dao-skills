# `dao-grill`：开工前最小对齐

`dao-grill` 在真正开始实现前，把一个尚不稳定的任务压成可执行的最小任务卡。它的目标不是制造更多计划，而是让人和 AI 知道：这轮究竟要让什么成立、哪些不做、哪里仍有风险、如何证明结果成立。

## 何时使用

- 用户意图、范围、验收或风险还不清楚。
- AI 已读到部分文档，但仍不确定应该先做什么。
- 一项需求可能很大，需要先切出一个可以验证的最小闭环。
- 即将开始线上修复、跨模块改动或有明显副作用的任务。

## 它不会替代什么

- 不写完整 PRD、技术方案或项目排期。
- 不替代代码设计、测试、review 和人的最终决策。
- 不在事实不足时伪装成“已经想清楚”，也不把所有问题一股脑抛回给人。

## 核心方法

`dao-grill` 先读现场，再给出当前理解；能基于已有证据推断的，不反问；只提出少量会改变方案、范围或验收的高杠杆问题。

最小任务卡至少包含：

```text
目标：这轮要让什么成立？
边界：明确不做什么？
风险：哪些依赖、假设或副作用仍不确定？
验收：用什么证据判断完成？
下一步：第一个可执行动作是什么？
```

## 输出与过门

输出通常是“当前理解 + Dao Grill Card + 过门判断”。过门结论只需明确三类：

- 可以开做；
- 先确认一项；
- 当前不应开做。

这样，任务不会因为内容很多就被假装成已准备好，也不会因为存在一点未知就无限停滞。

## 最小使用示例

```text
我要给订单模块补一个导出能力，但还不确定权限、数据范围和验收。
请用 dao-grill 先读取现有任务和代码约定，给出最小任务卡；
只有会改变实现路线的问题再问我。
```

## 与其他 skills 的关系

- 新伙伴或新项目尚未完成身份校准时，先用 [`dao-intro`](dao-intro.md)。
- `dao-grill` 解决“能不能开始”；实现中断时用 [`dao-handoff`](dao-handoff.md)。
- 实现、自测后，用 [`dao-review`](dao-review.md) 判断“能不能收口”。
