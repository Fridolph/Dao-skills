# Skills 协作地图

skills 不是代替工程能力的自动化流水线，而是在高频协作节点上，帮助人和 AI 先问对问题、留下足够信息。

## 三件套与两条旁路

```text
                 dao-role-map
                      |
任务模糊 -> dao-grill -> 开发 / 测试 -> dao-review -> dao-commit
                         |              |
                         |          dao-handoff（中断或换人）
                         |
                    dao-return-dao（经验成熟后）
```

| Skill | 所属位置 | 核心问题 | 不该代替什么 |
| --- | --- | --- | --- |
| `dao-grill` | 开工前 | 目标、边界、风险、验收够不够开做？ | 详细设计或代码实现 |
| `dao-handoff` | 流转中 | 下一位怎样无损接棒？ | 项目管理系统或完整复盘 |
| `dao-review` | 收口前 | 本轮真的能交付吗，还差哪一门？ | 代码 review、测试和 CI |
| `dao-commit` | L3 锚点 | 相对基线，系统真正发生了什么变化？ | 人的最终定锚与普通提交 |
| `dao-role-map` | 旁路：身份归位 | 养分、根、干、枝、叶分别是什么？ | 今天的任务排期 |
| `dao-return-dao` | 旁路：归母判断 | 这条经验是否跨项目成熟？ | 单项目复盘或随手收纳 |

## 一轮任务怎样组合

### 任务刚出现

目标不稳、范围容易膨胀、验收缺失，先运行 `dao-grill`。它的输出应是一个可以被项目执行的最小任务卡，而不是一篇说明书。

### 正在实现

继续使用项目原有的编码、测试、Issue 与 Git 机制。若窗口切换或多人接手，用 `dao-handoff` 把目标、状态、下一步、自测、文档锚点、收口候选交清。

### 准备收口

先使用 `dao-review`。它可以判定可收口，也可以要求补一项，或明确暂不建议收口。它不因为“改动多”就自动要求 Dao Commit。

### 发生真实变化

日常任务收口不使用 `dao-commit`。只有多个普通提交在 `feature -> dev` 或 `dev -> main` 合并 / squash 后，才用它读取 Git 净变化与日志，再由人确认“真实变化”后起草；卦象是集成锚点，不是装饰。

### 出现可复用经验

当一条规则已经不只属于当前项目，且有真实验证依据，再用 `dao-return-dao`。输出只能是：留在分支、候选观察、可以归母。先判断成熟度，再谈写进哪里。

## 主线失焦时的特殊入口

当问题不是“下一步改哪个文件”，而是“学习、项目、表达为什么都在争主位”，先用 `dao-role-map`。它以“养分 -> 根 -> 干 -> 枝 -> 叶”重新归位，再回到具体任务。

这不是价值排序，而是时位判断。一个分支项目可以很重要，但不应在母体尚未稳定时反过来定义根命题。

## 最小成功标准

这六个 skill 不需要一次全装全用。第一轮只要做到：

1. 用 `dao-grill` 压清一个任务。
2. 在中断时留下能接住的 `dao-handoff`。
3. 在收口前由 `dao-review` 给出明确结论。

当这三点能在真实项目中反复跑通，再逐步扩展到语义提交和归母判断，才不会让“skills 很全”掩盖“流程没跑通”。
