# 实践与验证

skills 化只是开始，不是“Dao-is-Coding 已经被证明成立”的结论。这个仓应该持续区分：哪些是已有实战依据，哪些是合理假设，哪些仍在等待反例。

## 当前已有依据

- 复杂报价状态模块曾按“起盘六问”完成重构，并通过实际主路径验证；它证明这项局部组织法在该场景有帮助。
- `Dao Commit` 已用于真实阶段性收口；它证明高信号语义锚点可以被写入 Git 历史。
- 任务状态、交接包和 review 收口已经形成可执行的最小形状。

这些不自动推出“任意团队、任意项目都会同样受益”。不同项目的规模、协作频率、工具链和人员经验都会改变结果。

## 使用与未使用的差别

| 维度 | 使用后的预期收益 | 不使用时常见的隐性成本 |
| --- | --- | --- |
| 开工 | 目标、边界、验收较早显性化 | 高效推进了错误或过大的实现 |
| 协作 | 换窗口、换模型时有明确接棒包 | 上下文依赖聊天记录和个人记忆 |
| 验证 | “测过什么、还剩什么”可被复查 | 用“应该没问题”替代证据 |
| 收口 | 自测、review、done 的边界更清楚 | 代码跑过却没人能接，也被误判完成 |
| 提交 | 关键变化可按语义检索和回看 | 历史只剩文件动作和低信号标题 |
| 沉淀 | 经验先经成熟度判断再升级 | 局部灵感过早变全局规则，或有效经验直接丢失 |

“不使用”不是做错。简单、短命、单人且上下文稳定的任务，用普通工程习惯可能更轻。Dao Flow 只应在协作不确定性、复杂度或长期可回看价值开始出现时增加最小必要承载。

## 怎样验证，而不是凭感觉相信

在同类任务中保留简短对照记录：

```md
任务：
复杂度 / 协作者 / 时长：
本轮用了哪些 skill，为什么：
开工前暴露了什么边界或风险：
中断后是否能直接接棒：
实际验证证据：
返工、误解或遗漏是否减少：
额外成本（时间、文档、沟通）：
结论：保留 / 调整 / 不适用：
```

优先观察能够反驳自己的指标，而不只收集顺利样本，例如：

- `dao-grill` 是否真的减少了范围回弹，还是只是多写了一页卡？
- `dao-handoff` 是否让另一位 AI 能在不追问的情况下完成第一步？
- `dao-review` 是否发现了实际遗漏，而不是重复已有测试清单？
- `dao-commit` 在数周后能否帮助人和 AI 快速理解“系统变成了什么”？
- 起盘六问是否降低了复杂模块的修改成本，还是只增加了命名和注释？

## 何时调整或停止使用

出现以下信号，应缩小或修订，而不是硬守流程：

- skill 产出长期重复项目已有文档，未提供新的判断。
- 为了填卡而填卡，实际验收仍然缺失。
- 每个小改动都使用 Dao Commit，导致历史噪音增加。
- 奇门或易经术语遮蔽了工程事实，让新协作者反而更难接入。
- 同一种流程在多个项目反复失败，说明假设、触发条件或输出形状需要重写。

最好的反馈不是“这套方法很有道理”，而是具体指出：它在哪个场景减少了黑盒，又在哪个场景造成了额外负担。
