# 开发运行流程

## 最小状态链

```text
planned -> designed -> in-progress -> self-tested -> review-ready -> done
                         |
                      blocked
```

| 状态 | 含义 | 进入下一状态前应确认 |
| --- | --- | --- |
| `planned` | 目标已出现，尚未形成可开发设计 | 意图、边界、验收与风险是否能说清 |
| `designed` | 已有可承接的最小设计 | 依赖、约束和验证入口是否足够开做 |
| `in-progress` | 有人正在持棒推进 | 当前改动是否仍在本轮边界内 |
| `self-tested` | 已完成本地验证 | 测试证据和未验黑盒是否已写清 |
| `review-ready` | 可以交给下一位 review | 交接包是否齐全，别人能否不靠猜接手 |
| `done` | 本轮范围已收口 | review 问题是否处理，结果是否已回主线 |
| `blocked` | 被明确阻塞，不是假推进 | 卡点是什么，怎样解阻 |

`self-tested` 不等于 `review-ready`：前者说明自己验证过，后者要求别人也能理解、复验和接手。

## L2：每次过门前问什么

`L2` 不替代状态机，它让状态不被过早跳过。每一次状态箭头前至少检查：

```text
口：当前真正困在哪个边界里？
意图：这轮要让什么成立？
边界：明确不做什么？
承载：下一位拿到的信息够不够？
风险：现在推进会不会越位或留下不可控影响？
验证：后面靠什么证明它成立？
```

当目标、边界或验收仍模糊时，调用 `dao-grill`。这是一种最小对齐，不是要求新增长文档。

## L4：开发现场怎样流动

实现过程中，项目原有的工程实践仍然是主体：设计、编码、测试、CI、PR、发布。Dao Flow 额外要求把“棒”保留下来。

每次中断、换模型或换协作者，至少留下：

```text
目标 / 状态 / 下一步 / 自测 / 文档锚点 / 集成锚点（如适用）
```

其中“下一步”不是宏大的未来计划，而是接棒人拿到上下文后的第一刀。`dao-handoff` 负责把这六项压成可读交接包。

## 验：不能只靠语气

当前将验证分为三类，按任务能力逐步落实：

- 机器验：类型检查、单元测试、构建、CI、真实接口或页面验证。
- 结构验：职责、依赖、输入输出、路径和写入点是否仍清楚。
- 意图验：最终结果是否仍服务最初目标、用户和承载边界。

每一类都应优先给证据，而不是“应该没问题”。

## 收口与沉淀

完成实现和自测后，使用 `dao-review` 先判断本轮是“可收口、需补一项，还是暂不建议收口”。通过之后：

1. 日常开发、流程修订与单任务收口使用普通 Conventional Commit。
2. 只有多个普通提交在 `feature -> dev` 或 `dev -> main` 合并 / squash 后，才使用 `dao-commit` 基于净变化起草语义锚点。
3. 若产生了跨项目可复用的经验，再用 `dao-return-dao` 判断它是留在项目、作为候选观察，还是可以归母。

重点不在于每一步都留下更多文档，而在于每次需要接、验、收时，信息都足以让判断不靠猜。
